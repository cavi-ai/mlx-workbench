# Strata inference

Strata is an optional, text-only runtime for Qwen3.8-Flash-Next on Apple Silicon. Workbench uses the pinned [Strata-MLX engine](https://github.com/yibie/strata-mlx) and [Strata HTTP frontend](https://github.com/Niko1221/Strata) behind mlx-agent's existing loopback serving, preview, receipt and stop operations. Ordinary MLX models keep their existing runtime selection.

## Install

Run `make install-strata` from the checkout with its initialized mlx-agent submodule. This requires `uv`, installs frozen dependencies in `~/.cache/mlx-agent/strata`, and downloads no model weights. It leaves the standard Workbench Python environment unchanged. `MLX_AGENT_STRATA_ROOT` can select another installation directory.

The engine and frontend revisions are pinned in `vendor/mlx-agent/src/mlx_agent/strata_runtime.py`. Serving checks their installed source fingerprint and the prepared model's file identities against the preview before launching. Installation refuses incompatible or modified source checkouts.

## Prepare existing files

Only the tested Qwen3.8-Flash-Next GSQ-RCO **Q2_0** and **IQ3_S** two-shard GGUF packs are supported. Reuse an existing compatible pair. MLX safetensors, VQ packs, other quantizations and companion/projector files cannot be used by this engine. A different supported GGUF pack is necessary when existing weights have one of those formats; Workbench never downloads it automatically.

Place both shards under one model directory. An optional complete MTP draft head must also be beneath that directory. The pinned engine's `tools/mtp_fetch.py` can fetch that head independently of the original model checkpoint; preparation verifies its manifest. Without MTP, suffix speculation remains available.

Use Strata's isolated Python to prepare the profile:

```bash
"$HOME/.cache/mlx-agent/strata/engine/.venv/bin/python" scripts/prepare-strata-model.py \
  --out /absolute/path/to/model \
  --gguf /absolute/path/to/model/Q2_0/Qwen3.8-Flash-Next-GSQ-RCO-Q2_0-00001-of-00002.gguf \
  --mtp /absolute/path/to/model/mtp
```

Omit `--mtp` when no draft head is present. Preparation exports the tokenizer from the same GGUF, writes a bounded `strata-model.json` profile and a runtime marker in `config.json`, and leaves weights unchanged. It refuses existing configs and symbolic links; a failed final validation removes its new metadata. Add this directory to the native app's model roots, then refresh the Library. Details labels the runtime **Strata (text only)**. Run and chat Compare use the existing serving flow; vision requests and LoRA adapters are unsupported.

## Serve and compare speculation

```bash
.venv/bin/python vendor/mlx-agent/scripts/mlx-agent serve start \
  --path /absolute/path/to/model --runtime auto --port 8084 --json
```

Inspect the preview, then repeat it with `--confirm --preview-hash HASH`. Prepared profiles resolve `auto` to Strata; explicit `--runtime strata` works too. Speculation defaults off. Add `--strata-speculation on` to both preview and confirmation to opt into draft-and-verify decoding. Compare throughput and first-token latency against ordinary decoding with the same GGUF weights before choosing it; draft overhead can make it slower. Add `--strata-expert-memory-gb 2 --strata-context-tokens 8192` to both commands to cap resident expert weights and context capacity. Expert budgets accept 0.5–64 decimal GB; context accepts 512–131,072 tokens. Omit the budget for automatic allocation. A smaller budget pages more weights from disk and can reduce speed. JIT serving supports the same profile and controls. The endpoint binds only to `127.0.0.1`, serves the OpenAI chat API, and preserves the local model path as its identity. Stop it through `serve stop --port 8084` so the receipt-owned process group is released.

Startup can take several minutes; Strata gets a bounded 900-second readiness window. Existing JIT memory admission and unload controls remain in effect. Performance depends on prompt length, draft acceptance, available memory and expert paging. Measure completion throughput and first-token latency separately. Quantization and floating-point execution can change responses; a faster run does not establish equivalent model quality. Workbench makes no universal speedup guarantee.

## Compare with an existing MLX model

Select the prepared Strata profile and an existing ready MLX model in chat Compare, then select one prompt set and run the comparison. Workbench warms each variant on the same endpoint used for its measured prompts and stops it before serving the next variant. Warm-up output is excluded from results. Server startup time is recorded separately from measured first-token latency.

Select the same prepared Strata model in two chat Compare lanes, then expand **Strata settings** within each lane. Choose speculation, expert memory and context capacity independently. Both lanes replay the same prompt set and output limits, sequentially, without copying or converting weights. Each lane retains its own settings, results and quality ratings; **Reuse setup** restores the selections and settings before a fresh run. Runs using custom settings or repeated model paths are excluded from default recommendations, aggregated model performance and winner promotion.

New chat results display answer text separately from a collapsible **Reasoning** section. They record the server's finish reason, generated token count, whether that count was estimated, total request duration and time until answer text begins. First-token latency can include reasoning; generation throughput counts all generated tokens, including reasoning. **Token limit reached** labels incomplete output, and an unreported finish reason stays unknown. These indicators describe generation, not factual answer quality. Historical text and runs without these fields are preserved.

New result cards retain the runtime, weight format and declared quantization from the confirmed serving preview. Strata results also retain its model and runtime fingerprints and draft-and-verify setting, expert budget and context capacity. Historical runs without this evidence show **Runtime not recorded**. Strata keeps the original GGUF quantized blocks and Metal execution path; comparison does not convert or download weights. Comparing a GSQ-RCO GGUF with an MLX VQ pack measures two model variants, so evaluate their recorded responses alongside speed before selecting a winner.

Strata memory admission excludes the disk-backed n-gram companion from resident weights. Automatic allocation estimates the first shard with a 20% expansion allowance. Explicit expert budgets instead read bounded GGUF tensor metadata and count capped expert weights, dense expansion and float prompt copies. Both include the full local MTP files, 5 GB of working memory and 30 KB per token at the selected context capacity. Eager serving retains 2 GB of headroom; JIT uses its selected headroom policy. Unknown tensor layouts, unavailable memory measurements or insufficient headroom block loading. These are admission estimates, not measured peak memory.

## Use a serving profile

On a completed Strata comparison lane, choose **Save serving profile…** and give the configuration a name. Saving records the settings without starting a server or marking them verified.

Select that model in Run, choose the saved **Serving profile**, and click **Verify profile**. Verification uses the existing canary prompts and output checks, allowing up to 1,024 generated tokens per prompt for reasoning and an answer. Missing or unfinished answers fail the gate. The recorded verdict binds the settings, canary version, model fingerprint and runtime fingerprint. Saving and verification never change runtime defaults or the shared application configuration.

After verification, **Preview serve** and **Confirm and run** carry the profile through the existing confirmation boundary. **Use profile for endpoint** applies it to the first always-on endpoint, with an explicit port and eager or load-on-request mode. Its fleet configuration retains the profile across relaunches; running endpoints must match the confirmed receipt identity. Changing a model through ordinary fleet actions clears its profile.

Profile serving resolves the current durable profile and rechecks its verification against a fresh serving plan before preview and start. Changed settings, model files, runtime sources, failed re-verification or unavailable profile state block new serving until verification succeeds again. Existing historical comparisons and default serving behavior remain unchanged. Profiles are stored separately in `serving-profiles.json`.

In Run, **Manage profile** offers **Rename…** and **Remove…** for the selected profile. Renaming preserves its identity, settings and verification. Removing requires confirmation and refuses profiles referenced by any configured endpoint, including disabled slots; replace that slot's serving configuration or remove the slot first. Both actions recheck the opened profile against its durable snapshot and leave the draft open when saving fails or the profile has changed. Neither action starts or stops a server, changes model files, or rewrites past comparisons. Successful removal returns the Run picker to runtime defaults.

## Compare memory and answer latency

New chat comparison lanes record system headroom before loading, its lowest sampled value during startup, warm-up and prompts, and the value before server cleanup. Readings run every half second, with explicit boundary readings; the result records successful and unavailable reading counts. Headroom uses the system's free and inactive pages as an estimate. It includes other applications and file caching, so it does not measure model-only RAM use or guarantee a peak between samples. Missing or invalid boundary readings leave memory evidence unavailable. Historical runs are not rewritten.

Completed chat runs show **Memory and answer latency**. Points pair the lowest sampled system headroom with median time to first answer, requiring finished answers and recorded answer timing for every prompt in the lane. The headroom target highlights observed tradeoffs without changing serving limits, starting another measurement, or choosing a winner. Completion alone does not establish task quality; inspect the recorded answers and ratings. Engine allocation is separately labeled **not reported** because the serving response does not expose it.

## Find settings for a Strata model

In chat Compare, **Find best settings…** prepares four lanes for one ready Strata model: two explicit expert-memory budgets, each with draft-and-verify off and on. Choose one fixed context, an observed-headroom target and a latency objective, then **Use setup**. **First answer** minimizes request-to-first-answer time. **Completed response** minimizes recorded request-to-stream-completion time, including reasoning and answer delivery; server startup and warm-up are excluded. This only changes comparison setup; **Run comparison** starts the existing sequential measurement flow. The same prompt set is replayed in every lane, and normal memory admission guards remain in force. The headroom target judges observed samples and does not reserve RAM or change serving limits.

The completed run retains its search goal. A suggested lane requires all four results, matching model/runtime fingerprints and recorded settings, valid memory evidence, and task reviews for every lane. Each recorded prompt must have valid server-reported input-token counts matching the sample's prompt length, with the same total, cached and new-token counts across all four lanes. Server processing times may differ. Missing or different cache work withholds the suggestion, so a lane cannot qualify by processing less uncached input. Older runs without this evidence retain their results but cannot supply a settings-search suggestion. The memory-and-latency panel explains the first unmet requirement; saving and verifying a suggestion rechecks the same eligibility against the durable run.

Eligible lanes need a quality score of 4 or 5, a complete timed answer for every recorded prompt, and observed minimum headroom meeting the target. The suggestion minimizes the selected latency objective's median among those lanes. Completion timing must be positive, finite and no earlier than the recorded first answer for every prompt; missing timing and unfinished answers exclude a lane from that objective. Results show the recorded objective in their suggestion, chart and lane timings. Older searches without an objective retain first-answer ranking, and existing runs are not rewritten. This is an observed comparison, not a guaranteed optimum. Cache matching does not control cache policy or remove sequential system-load variation. Save the lane as a serving profile and pass its canary verification before serving. Manual lane edits must retain the four-lane search cohort or switch explicitly to a manual comparison. Reused setups remain ordinary comparisons until a new settings search is prepared.

The suggested lane offers **Save and verify suggestion…** directly in its result card. Enter a profile name and explicitly start verification. The saved profile records its source run and lane; retries in the dialog reuse that profile. Verification rechecks the durable comparison, its eligibility and the recorded fingerprints/settings before loading, and rechecks the comparison again before publishing a verdict. Changed or unavailable evidence leaves verification unsuccessful. Canary failures remain visible for review. After a pass, **Open Run** selects the verified profile without starting a server; Preview and Confirm remain separate actions. Starting another comparison is disabled while profile verification is in flight.

In Run, **Comparison evidence…** reads the selected profile's saved source run and lane. It shows recorded median time to first answer, sampled system headroom and the current saved task review, separately from the canary verdict. Opening the dialog loads neither a model nor a server and writes no state. Missing sources, changed settings and fingerprints that differ from the profile's verification are reported instead of substituting another comparison. Older profiles without source identities remain usable through their existing verification flow. Recorded headroom is historical and includes other apps and file caching; serving retains its current memory admission checks.

**Manage profile → Customize copy…** opens the selected profile's settings in a draft. Change its name, speculation, expert-memory budget or context, then **Save copy** to create and select a new unverified profile using the same local model. Save rechecks the original profile; changed or missing sources and failed writes retain the draft. Cancel writes nothing, and edited drafts require explicit discard. Original profiles and endpoint references are preserved. Every copy requires its own canary verification. A settings-identical copy retains its source-comparison link; changing settings clears that link so the original measurements are not attributed to the new configuration.

**Manage profile → Compare profiles…** prepares two saved configurations for the same local Strata model, with the selected profile in lane A. Choose a profile with different settings for lane B, then **Use setup** to open Compare. Both profiles are rechecked against their saved snapshots before setup is applied. Choose one shared chat prompt set and explicitly **Run comparison** to measure the lanes sequentially. Results retain recorded profile names, settings and fresh runtime evidence; manual settings changes omit profile labels when they no longer match. Preparation saves nothing and starts no inference. Measurements never change profile verification, endpoint configuration or the original profiles. An unverified copy remains unverified after comparison.

A completed profile lane with finished text answers offers **Verify measured profile…**. Review the current profile and explicitly **Attach and verify** to link that recorded comparison to the same profile ID and run fresh canaries. Starting clears the previous canary verdict. The durable comparison and current profile must still match; model/runtime fingerprints and settings are checked before loading, and the comparison is checked again before publishing verification. Failures after attachment leave the profile unverified, with its measured source retained. Retries reuse that profile. A pass offers **Open Run** without starting serving; Preview and Confirm remain explicit. This action creates no new profile and does not change endpoint configuration.

In Run, **Review profiles…** lists saved configurations for the selected model with their canary status and available source-comparison measurements: median first-answer latency, lowest sampled system headroom and task review. Each measurement retains its prompt-set name and recording date; missing or mismatched evidence is labeled unavailable. Headroom is historical system-wide availability, including other apps and file caching, rather than model-only RAM or current free memory. **Select profile** rechecks the displayed profile and comparison before returning to Run. Changed snapshots require **Refresh profiles**. Selection writes no configuration and starts no inference; unverified profiles still require canaries, and serving retains Preview and Confirm.

Each profile's **Check memory** action requests a fresh, unconfirmed runtime preview and captures available system RAM once. It displays the runtime's memory estimate, the reading time and whether the saved canaries still match the preview's model, runtime and settings. Unavailable RAM is labeled explicitly. The estimate excludes eager serving's additional headroom reserve; it is neither measured model allocation nor an admission verdict. Available RAM includes reclaimable inactive pages and can change immediately. Confirmed startup keeps its existing memory guard, and load-on-request endpoints keep their configured policy. The check loads no model, saves no verdict and changes no endpoint. Profile or comparison changes during the check reject its result; Refresh profiles clears captured checks.

New chat samples retain server-reported draft tokens offered and accepted when the final response supplies both counts. Strata result cards and the text A/B inspector show the counts and their acceptance percentage per prompt. An explicit zero reports no draft tokens without inventing an acceptance percentage; missing, invalid or conflicting counts remain unreported. Historical runs are not rewritten. The counts describe draft-and-verify decoding, including copied suffix guesses when reported by the runtime. Compare answer quality, answer latency and throughput separately: acceptance alone establishes neither correctness nor a speedup. Warm-up requests remain excluded from recorded comparison samples.

New samples also retain reported new and cached input-token counts and server prompt-processing time when the counts match the reported prompt length. Result cards and the text A/B inspector show this evidence separately from client first-token latency. Server prefill speed uses new tokens over the reported server time; fully cached prompts and zero-duration readings have no computed speed. Fresh client prefill estimates use reported new-token counts when available; estimates without this evidence use the full prompt length with unknown cache use. Missing, invalid or conflicting reports remain unavailable. Historical measurements are not recalculated, and these diagnostics do not change cache policy, quality ratings or profile eligibility.

Completed chat runs with one speculation-off and one speculation-on lane for the same model, signature, explicit expert budget and context show **Paired speculation observations**. Each budget is compared separately. A numeric summary requires complete matching prompt cohorts, matching model/runtime and recorded environment fingerprints, finished answers, equal reported generation counts and identical recorded cache work for every prompt. Missing or differing evidence withholds the whole pair's summary. The decode figure is the median of per-prompt client decode-rate ratios (on divided by off); answer-start medians are shown separately. Per-prompt observations and saved task ratings remain available for inspection. These sequential observations do not establish general speedups or answer quality, and they never select, verify or activate a serving profile.
